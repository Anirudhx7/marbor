Deployment-aware placement

Every request is evaluated against model residency, runtime compatibility, deployment constraints, GPU groups, free capacity, health, queue depth, and warm state. The best fit wins, not round-robin.

Already on LiteLLM? Keep it: Apps → LiteLLM → Marbor → runtimes → GPUs. LiteLLM handles keys and fallbacks; Marbor owns placement onto real hardware. Centralizing cloud on one contract? Marbor → LiteLLM → cloud works too.
What LiteLLM can't see from above: free VRAM per node, which runtime serves which model where, live load per GPU, which node already holds the model warm, whether a retry is stream-safe, which sessions must stay local, and which GPUs to prewarm or drain. That is the layer Marbor adds underneath.

FAQ

What operators ask before installing.

Short answers, no hype.

What is Marbor? −

Marbor is the control plane for self-hosted inference: a static binary on your gateway, with an optional marbor-agent on GPU nodes for live GPU telemetry. It places each request across Ollama, vLLM, TGI, llama.cpp, and MLX behind one OpenAI-compatible endpoint.

How is it different from nginx? +

Nginx routes connections blindly. Marbor reads live fleet state: model residency, runtime, VRAM, in-flight load, and health, and places each request where it can actually serve.

Does it do distributed inference (TP/PP/expert routing)? +

No, and it never claims to. Parallelism, sharding, and KV transport stay inside the runtime (e.g. vLLM). Marbor selects the right deployment and observes the result.

Can it replace cloud APIs? +

Marbor is designed to serve inference from your own GPUs first, with optional cloud overflow to OpenAI or Anthropic when local capacity is saturated, metered per token.

How does HA work? +

Unhealthy nodes are excluded automatically after consecutive failed polls; saturated queues spill to configured, metered cloud overflow or a 503. Marbor itself runs as a single process. For gateway redundancy, place two independent instances behind an L4 balancer; in-flight requests on a failed instance are lost.

Auth and limits? +

Bearer keys, per-key model allow-lists, daily/monthly quotas. Protect GPUs without app changes.

Does Marbor look at my prompts? +

No. Placement uses only the model name, session id, and request path. Prompt text is never parsed for routing, and KV data never moves between nodes.

What happens in a traffic burst? +

When the overflow queue is enabled and has room, bursts wait up to queue_timeout_ms (or your overflow SLA) for a slot, then try any configured local alternate, then spill to configured metered cloud or a 503.

What if a node dies mid-request? +

If nothing has streamed yet, the request retries on a healthy node. A stream in flight is never replayed.

Does Marbor learn my workload? +

Yes. Sequence and time-of-day patterns drive predictive prewarming (when size and headroom are known), pinned models are never evicted, and warm state is restored after restarts.

Can I see why a request landed where it did? +

Yes. Each locally-routed request records a routing explanation, reason plus score breakdown, viewable per request in the dashboard and via the requests explain API.
