# Changelog

All notable changes to this project will be documented in this file.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Added
- **CLI persistent auth: `ollama-mesh login`/`logout`/`whoami`, so every other command can stop passing `--token`/`--username`/`--password` on every single invocation.** `ollama-mesh login` authenticates once (interactively - password input is not echoed - or via `--username`/`--password`, or `--token` to save an existing token) and persists the resulting session to a local file (`0600`, under `os.UserConfigDir()`); every other credentialed command (`nodes`, `models`, `runtime`, `node control`) now falls back to that saved session as the lowest-priority credential source, after `--token`/`MESH_TOKEN` and `--username`/`--password`/`MESH_USERNAME`+`MESH_PASSWORD` - a saved session is never used against a different `--server` than the one it was authenticated against, so juggling multiple mesh instances from one machine can't cross-wire tokens. The saved file deliberately never stores an expiry timestamp - the server remains the sole source of truth for session validity, discovered via a real 401 (which now also prints a "run ollama-mesh login again" hint when the expired credential came from the saved file specifically). `ollama-mesh whoami` reports the saved identity, live-verified with one request against the Admin API rather than trusted from the local file alone; `ollama-mesh logout` deletes the saved session and is idempotent. No Admin API or SQLite schema change - this reuses the existing `POST /admin/v1/login` session-cookie mechanism as-is.
- **CLI Group 2 parity: `mesh models pull|delete|unload|list` and `mesh runtime drain|undrain|health` — closing the last gap between the Admin API/UI surface and the official CLI.** An audit found the Admin API and UI already fully supported model pull/delete/unload/list (per-node) and runtime drain/undrain/health-check, but the CLI (`internal/cli`) had zero commands for any of them, despite exposing the identical `/admin/...` routes the UI already calls. `mesh models pull <node> <model>` (async, mirrors the UI's fire-and-forget pull flow), `mesh models delete <node> <model>`, `mesh models unload <node> <model>`, `mesh models list <node>` (the per-node local inventory, distinct from the existing fleet-wide `mesh models`), `mesh runtime drain <node> [--reason=X]`, `mesh runtime undrain <node>`, and `mesh runtime health <node>` (an on-demand active liveness probe — a populated `ok:false` result is a successful probe reporting a down runtime, not a CLI failure) now all exist, each exactly one Admin API request per the CLI's existing contract. No new Node Agent Protocol capability, Admin API route, or UI surface was added — a `diagnostics.health` capability originally proposed for this item was deliberately not built as a new capability; it would have duplicated the existing `runtime.health_check` (now exposed via `mesh runtime health`), so the CLI gap was closed against the existing capability instead. A permanent "CLI parity" rule has been added to the workflow's Definition of Done: no new Web UI operation may ship without a corresponding CLI command, to prevent this gap from re-accumulating.


- **A manually or scheduled-unloaded keep-warm model is now visible on the dashboard instead of just sitting cold with no explanation.** The suppression that makes an unload "stick" until an explicit rewarm previously had no admin API or UI surface at all - an operator saw a keep-warm-configured model stay cold with no way to tell "deliberately suppressed" from "warmup broken" from "never scheduled." `GET /admin/nodes` now includes a `warmupState` array per node (model, state, reason - `manual_unload` or `scheduled_unload` - and since timestamp); the Warmup & Scheduling page's per-model rows show "Suppressed - unloaded by schedule, resumes on next warmup" in the same slot as a warmup-failure message, and GPU Nodes gets a `SUPPRESSED (n)` badge alongside the existing WARMUP FAILED/UNLOAD FAILED ones. The raw internal suppression map/bool is never exposed directly.
- **`runtime.logs` (P58) - fetch recent log lines from a node's inference runtime process, closing the last Phase-3 gap left by P43.** Once an operator has accepted a control driver for a node, a new "View Logs" button on the GPU Nodes page's Runtime Control panel - and the equivalent `mesh runtime logs <node> [--lines=N]` CLI command - fetch a point-in-time snapshot of the runtime's recent output, wherever the accepted driver knows to look: `journalctl -u <unit>` for systemd, `docker logs --tail` for Docker, `log show` for launchd, and Windows Event Log (`wevtutil`) for a Windows service. This is a snapshot fetch, not a live tail - no streaming/follow flag is used on any driver. The Process driver (a bare PID file with no supervisor) has nothing to read logs from and returns a clear "not supported without a supervisor" error rather than guessing, matching how it already handles Start/Stop with no supervisor configured. New agent route `POST /v1/runtime/logs`, new capability `runtime.logs`, new Admin API route `POST /admin/nodes/{name}/runtime/logs`. Unlike start/stop/restart, this is a pure read and is not audit-logged.
- **`runtime.stop`/`start`/`restart` are now live end-to-end (P43 Step 3), on top of the ControlDriver registration flow shipped earlier.** Once an operator has accepted a control driver for a node (GPU Nodes page's "Runtime Control" panel, or `mesh node control accept`), Start/Stop/Restart buttons - and the equivalent `mesh runtime start|stop|restart <node>` CLI command - actually start/stop/restart the inference runtime process via the agent's systemd/Docker/process/launchd/Windows-service driver. The mesh never asks the agent to guess: it builds `{driver, identifier}` from its own store-backed config on every request and sends it fresh, so the agent itself holds no persisted control state. A node with nothing accepted returns a clear "Runtime control unavailable: no control driver configured" (422) rather than a guess. The Process driver's `Start` also needed a launch command Step 2 never persisted - a new optional `start_command` field (added to the existing `node_control` table, not a new one) is set once at Accept time and only ever sent back for that driver's Start action. New agent routes `POST /v1/runtime/{start,stop,restart}`, new capabilities `runtime.start`/`runtime.stop`/`runtime.restart`, new Admin API routes `POST /admin/nodes/{name}/runtime/{start,stop,restart}`.
- **Node Agent gained a ControlDriver registration flow - the foundation for `runtime.stop`/`start`/`restart` (P43).** A new `ControlDriver` abstraction, orthogonal to runtime detection, answers "how does the agent start/stop/restart the inference runtime process" (systemd unit, Docker container, PID file, launchd label, or Windows service - v1 covers all five). The agent probes its host (confidence-ordered: service manager, then container, then PID file, then a reachable port as a last resort that never selects a driver) and reports what it found; an operator reviews the evidence and explicitly accepts a driver + identifier from the GPU Nodes page's Manage Node Agent modal (new "Runtime Control" section) - a later re-scan can surface a different suggestion, but never silently switches what's accepted. New `GET`/`POST .../accept`/`DELETE /admin/nodes/{name}/control` endpoints; new additive `control` object in the agent's `/v1/status` payload. The actual `runtime.stop`/`start`/`restart` capability wiring (agent action handlers, admin API dispatch, `mesh runtime` CLI commands) lands in a follow-up - this ships the discovery/configuration foundation it depends on.
- **New `mesh` CLI - a thin, read-only client of the Admin API.** `mesh version`, `mesh status`, `mesh nodes`, and `mesh models` are the first four commands, each exactly one Admin API request (never talking to a Node Agent directly). `--json` ships on every command from day one - that's the real compatibility contract, human table output is not - and every command follows a fixed exit-code convention (0 success, 1 user/input error, 2 server error, 4 auth failure). `nodes`/`models` need a session, obtained via `--token` or `--username`/`--password` (which the CLI exchanges for a token through the existing `POST /admin/v1/login`); `status`/`version` need no auth. Build with `make mesh-cli` or `go build -o mesh-cli ./cmd/mesh`; goreleaser now publishes `mesh-<os>-<arch>` binaries alongside the existing `ollama-mesh-<os>-<arch>` ones. No `restart`/`stop`/`start`/`delete`/`drain` commands yet - those need a real `ControlDriver` first. `scripts/smoke.sh` now builds the CLI and runs `status`/`nodes`/`models` against the live demo stack's Admin API as its final step, so the CLI is gated the same way as the proxy/admin/metrics surfaces on every smoke run.
- **Admin API v1 surface audited for CLI/SDK consumption; one gap closed.** `POST /admin/login` was the only admin route missing its `/admin/v1/` twin (every other route already had one via the existing route-mirroring helper) - a v1-only client would have had to special-case login. `POST /admin/v1/login` now works identically to the existing `/admin/login`.
- **The Models page now warns when the same model name has different content on different nodes** (e.g. the same tag re-pulled with a different quant/build mid-rollout, without every node picking up the change yet). Ollama already reports a per-model content digest that the mesh previously discarded; it's now tracked per node and, when two or more nodes disagree on it for the same model name, a warning badge appears on that model's card, with each node chip's tooltip showing its own digest so you can see which node is the outlier. Other runtimes (vLLM/TGI/llama.cpp/MLX) don't expose a comparable digest today, so this check is silently skipped for them rather than guessing.

### Changed
- **The admin CLI's `--token`/`MESH_TOKEN` credential flag has been removed outright (no deprecation period).** A bearer token passed as a CLI argument or read from an env var is still visible in shell history, `ps`/Task Manager, and process-creation logging for the life of the process - the same exposure class already fixed for the Node Agent's own `--token` flag. Unlike that case, the admin CLI has no external users yet and `ollama-mesh login`/`logout`/`whoami` (persisted session file) plus `--username`/`--password`/`MESH_USERNAME`+`MESH_PASSWORD` already cover every legitimate credential path, so there was no compatibility reason to keep a warn-then-remove window open - it's gone now. `--token` is an unrecognized flag on every command as of this change.
- **BREAKING: the standalone `mesh`/`mesh-cli` binary (`cmd/mesh`) has been merged into the main `ollama-mesh` binary.** ollama-mesh is a single static Go binary by permanent design - shipping a second binary for the Admin API CLI violated that. `ollama-mesh version`/`status`/`nodes`/`models`/`runtime`/`node control` now dispatch from the same binary as the server and the existing `agent`/`bench` subcommands, reusing the exact same `internal/cli` logic unchanged; `ollama-mesh --help` now shows one unified command table covering the server, Node Agent, benchmark tool, and Admin API CLI instead of separate help systems. Every existing server flag (`--db`, `--seed-node`, `--log-format`, `--version`) and `install.sh`'s invocation pattern keep working byte-for-byte identically. There was no external usage of the standalone `mesh`/`mesh-cli` binary (beta, no released users), so it was removed outright with no alias or migration shim - `go build -o mesh-cli ./cmd/mesh` and goreleaser's `mesh-<os>-<arch>` release asset no longer exist as of this change.

### Fixed
- **`ollama-mesh bench --help`, `ollama-mesh agent --help`, and `ollama-mesh agent service install|uninstall --help` wrote their help text to stderr instead of stdout**, inconsistent with the GNU convention (`internal/cli`'s commands, `agent service start|stop|status --help`) already established elsewhere in the same binary. Each now intercepts `-h`/`--help` before `flag.FlagSet.Parse` runs and prints to stdout, exiting 0 - a genuine bad-flag error still prints to stderr with a non-zero exit, unchanged.
- **Model Advisor's Pull button only ever appeared for Ollama nodes, even when a node's Node Agent already supported pulling models for vLLM/TGI/llama.cpp/MLX** (`internal/nodeagent/actions.go`'s `pullCommands` map has real entries for all five runtimes). The UI hardcoded `runtime === 'ollama'` instead of asking whether the node's agent actually advertises the `models.pull` capability - the same check `handleNodePull` already uses server-side to choose direct-vs-agent dispatch. The model catalog API (`GET /admin/models/catalog`) now includes each node's `runtime` and effective `capabilities` (mirroring the admin API's own dispatch decision - a node whose agent is present but disabled in settings correctly reports none), and the Pull button shows whenever the node is Ollama or its agent capability list includes `models.pull`.
- **`free_vram_headroom` placement scoring misread vLLM's static KV/weight pre-allocation as VRAM pressure (P62).** vLLM reserves its configured `gpu-memory-utilization` (commonly 0.8-0.9) at startup, so an idle, fully-able-to-serve vLLM node reported ~90%+ VRAM used by design and scored ~1.6 of a possible 20 on that factor, versus ~18 for an idle Ollama node - in a mixed fleet, vLLM nodes were systematically deprioritized for cold-start placement even when correct. Placement now detects static-reservation runtimes (vLLM today; TGI's static mode is deliberately deferred pending confirmation against real telemetry) and scores that factor from in-flight request count instead of free bytes, neither crediting nor penalizing the reserved block. Warm-resident routing (weight 50) was never affected - this only distorted cold-start placement. No config/schema change, no new scoring factor, existing weights unchanged.
- **The Predictive Warmup Engine could silently reload a model an operator had manually or scheduled-unloaded**, if that same model also happened to be a likely-next model in the transition history or a time-of-day pattern - overriding the operator's explicit "keep this cold" decision the same way the periodic keep-warm pinger used to before it respected unload suppression. Both of the engine's warmup trigger points (transition-based top-3 prediction and time-of-day prewarm) now check the same suppression state the manual/scheduled unload path sets, and skip a suppressed model instead of reloading it - visible in the Predictions tab as a normal "skipped" decision, same as any other unmet prediction.
- **A drain didn't actually keep a node empty if any keep-warm config or warmup schedule was still active for it.** Both the periodic keep-warm pinger and scheduled/manual warmup (`WarmModels`) loaded models with no check of the node's draining state - routing and eviction already correctly skipped draining nodes, but warmup itself was never wired to respect it, so a drained node's keep-warm models got silently reloaded on the very next warmup tick. Both paths now skip a draining node entirely; a "warmup" schedule fired against a draining node now records `last_status: error` instead of a false "ok".
- **The Node Agent is now host-scoped: one physical machine running multiple runtimes (e.g. Ollama on :11434 and vLLM on :8000 on the same box) needs exactly one agent process/enrollment, and every node row on that host now correctly shows "Agent" instead of only whichever node happened to be enabled first.** Previously each node row got its own independently-generated bearer token, but only one running agent binary could ever hold the matching token - every other node on the same box would poll with the wrong token, get a 401, and permanently show "No Agent." The agent itself now detects every runtime listening on its host each cycle (not just the first one found) and reports them all; each discovered runtime gets a stable, opaque identity (independent of its type name or port, so reconfiguring a runtime's port never changes its identity) persisted locally by the agent. `NodeState.Host` (new, defaults to the node's own URL hostname - no action needed for existing single-runtime installs) groups node rows that share a physical machine; the mesh now polls each host's agent exactly once per interval (not once per node) and fans the result out to every node on it. New optional `host` field on the add-node API/config (`internal/store` `runtime_nodes.host` column, additive), new additive Node Agent Protocol fields (`Telemetry.Runtimes[]`, `RuntimeInfo.id`/`.port` - `ProtocolVersion` unchanged, old agents/mesh binaries keep working via the existing singular `runtime` field). Known limitation, not yet handled: two separate instances of the *same* runtime type on one host (e.g. two vLLM processes) can't be told apart by type alone and fall back to port-based matching, same as before this fix.
- **Runtime Control's discovery could match the Node Agent's own service instead of the runtime it was looking for** (e.g. systemd unit `ollama-mesh-agent.service` contains the substring `ollama`, the runtime name being searched for), and separately, **Start/Stop/Restart/Logs were gated on runtime health instead of agent reachability** - stopping the runtime intentionally (as designed) made the router mark it unhealthy on its next poll, which then blocked Start from ever dispatching again through the same gate, a functional dead end. All four discovery probers (systemd/launchd/Windows service/Docker) now exclude the agent's own registered service name before matching, and the runtime start/stop/restart/logs handlers now gate on the Node Agent's own reachability (already tracked independently for telemetry purposes) rather than the runtime's. The "Set Manually" control-driver form no longer silently pre-fills its Identifier field from a (possibly wrong) discovery result while leaving the Driver dropdown on an unrelated default, and now requires an explicit confirmation step before persisting, matching Start/Stop/Restart's existing confirm dialog - both real contributors to nodes ending up misconfigured with the wrong driver.
- **Windows Node Agent service reinstall/upgrade could fail with a port-already-in-use error, and `install.ps1` could fail to even download a new version over a running install.** `sc stop` only requests a stop and returns immediately, without waiting for the old process to exit - `windowsManager.Install` now polls for the service to actually stop (10s timeout) before starting it again, closing a race where the new instance's bind could hit the old process still holding the port. Separately, Windows locks a running `.exe`'s file, so `install.ps1` re-downloading `ollama-mesh.exe` over an already-installed, running agent service failed outright; the script now stops that service first (if present) and waits for it to exit before downloading. Neither race exists on Linux/macOS, where `systemctl restart` is atomic and a running binary's file can be replaced freely.
- `install.ps1` now pauses with "Press any key to exit..." before the window closes (skipped when non-interactive, e.g. `$env:CI` set) - previously the console vanished the instant the script finished, whether launched via a double-clicked shortcut or the enroll one-liner's `powershell -Command "...; irm ... | iex"`, taking the install summary or any error message with it.
- **Running `ollama-mesh.exe` (or `ollama-mesh agent ...`) directly and hitting a fatal error (bad `--db` path, port already bound, invalid config, etc.) still closed the console instantly on Windows** if launched without an existing shell keeping the window open (double-click, a desktop shortcut, Explorer) - the error was on screen for one frame and gone. Every `log.Fatalf`/`os.Exit` call site in `main.go` and `internal/nodeagent` now routes through a shared exit path (new `internal/winexit` package) that, on Windows, pauses for a keypress only when the process owns its own console (`GetConsoleProcessList` reports just this process attached) - already-open terminal usage is unaffected. No behavior change on Linux/macOS.
- **Re-uploading a backup file you'd already downloaded (or a scheduled backup firing when mesh.db hadn't changed since the last run) silently added a byte-for-byte duplicate to the restore list**, under a new timestamp with no indication it was identical to one already there. Both entry points into the backup pool - `POST /admin/backup/upload` and the scheduled backup job - now hash the file (SHA-256) and check it against every existing backup in the target directory before saving; an upload that matches an existing file reuses that file instead of adding a copy, and Settings shows a clear notice ("This is the same backup as `mesh-backup-<timestamp>.db`, already in the list") instead of silently selecting it. A scheduled run that would produce an identical file is skipped (still recorded as a successful run, so the scheduler doesn't retry every tick) rather than cluttering the list.
- **Two concurrent requests for different cold (not-yet-loaded) models could both get routed to the same node**, each seeing the same stale last-poll VRAM snapshot and neither aware the other had just claimed headroom there, before the next poll cycle could catch up - a real double-booking risk on the VRAM-aware placement the mesh is built around. Cold-start routing now writes a lightweight, in-memory VRAM reservation the instant a node is picked, and placement scoring discounts a node's free-VRAM headroom by whatever's already reserved-but-unconfirmed there - closing the race without adding any blocking work to the request path (a live poll confirming the model resident clears the reservation immediately, rather than waiting out its 5-minute safety TTL). This reservation is now written as soon as a node becomes the leading scoring candidate rather than only after every candidate has been scored, narrowing the same race further.
- **Every inference request paid for up to three synchronous SQLite writes on the request path** (an audit-log insert, an hourly-bucket upsert, a model-stat upsert) before the response could even be attributed. Audit-log entries and local-request stats now go through the same bounded async queue the request-log already used, off the request path entirely. Cloud-request stats stay synchronous on purpose - the daily/monthly cloud spend cap reads that exact write in real time, and making it async would let a burst of requests blow past a configured budget cap before the writer caught up.
- **A node that just crashed kept scoring as if its last-known VRAM/queue/loaded-models snapshot were still fresh** for the full grace window before health checks flip it unhealthy (several consecutive failed polls). Placement scoring now applies the same penalty an upstream-error cooldown already gets once a node's telemetry is older than that grace window, instead of trusting a snapshot that's actually gone stale.
- **A model name re-pulled with different underlying weights on some nodes but not others (a mid-rollout update, a mismatched quantization) was invisible to routing** - warm-residency scoring and session pinning treated every node's copy under that name as fully interchangeable. The router now remembers the first-observed content digest per model name and stops crediting a digest-mismatched copy as a warm hit; a runtime that doesn't report a digest (anything but Ollama today) is never flagged.
- **Sticky-session pinning was in-memory only - a mesh restart dropped every in-flight session**, forcing a cold KV-cache round-trip on each one's next request. Session affinity is now persisted and restored on the same schedule as warm state; an entry already past its TTL at restore time is skipped rather than restored and immediately swept.
- **`install.sh`/`install.ps1`'s `TOKEN=` (legacy/manual) Node Agent install path re-serialized the token it already had as an environment variable back into a `--token=` CLI argument** when handing off to `ollama-mesh agent service install`, exposing it via `ps`/Task Manager for the life of that one-shot install process. Both installers now rely on the binary's existing `TOKEN` env var fallback instead of passing `--token` at all (`install.sh` additionally uses `sudo -E` so `TOKEN` still reaches the child process when installing without root). Directly passing `--token=<token>` to `ollama-mesh agent` or `ollama-mesh agent service install` still works unchanged, but now prints a one-line deprecation warning to stderr pointing at the `TOKEN` env var / `ENROLL` flow instead; the flag itself is deprecated, not yet removed.

## [0.18.0] - 2026-07-30

### Changed
- **Open WebUI integration guide overhauled based on real-world testing against current Open WebUI releases.** OpenAI-compatible connection is now the primary recommendation (Ollama-native's API key field is inconsistent across Open WebUI versions), Docker Compose is now the lead example, and new sections cover Desktop-vs-server, localhost-vs-LAN-IP, Docker networking, and a connectivity check to run before touching the Open WebUI UI at all.

### Added
- **mesh.db now has a real backup story: manual download plus scheduled auto-backup, both from a new Settings > Backup & Restore card.** Until now there was zero backup mechanism anywhere - losing `mesh.db` meant losing every node, API key, routing rule, and setting with no way back. "Download Backup Now" streams a consistent point-in-time copy (SQLite `VACUUM INTO`, safe alongside live traffic) straight to your browser; Scheduled Backup lets you enable automatic backups with a configurable interval (hours) and retention (how many backup files to keep, oldest pruned first), writing to a configurable target directory (`GET`/`PUT /admin/settings`'s new `backup` object, `POST /admin/backup` for the manual download). `docker-compose.yml` gained a second named volume (`mesh-backups:/backups`, `MESH_BACKUP_DIR` env), kept deliberately separate from the existing `mesh-data:/data` volume - so deleting the container, or even wiping the data volume, doesn't take the backups down with it, and vice versa. The same card can also restore a listed backup with one click (see next entry); a fully manual fallback (`docs/backup.md`) remains for anyone not running under a process supervisor, and restore is never restricted to any particular directory - any backup file works from any path, on Docker or bare metal alike.
- **The restore picker's file list no longer grows unbounded on screen** - it's now a single dropdown (select the backup, one fixed Restore button next to it) instead of one row per file, which would have kept expanding forever as scheduled backups accumulate. A new **+** button next to it lets you attach any `.db` file from your own machine (a plain `<input type="file">`, so it works the same on Chrome/Firefox/Safari/Edge across Linux, Windows, and macOS) - the mesh validates it's a genuine SQLite database (the same `PRAGMA quick_check` every other backup path uses) and saves it into the same target directory under the standard `mesh-backup-<timestamp>.db` name, so it shows up in the dropdown and restores exactly like a scheduled backup. A spinner replaces the **+** icon while the upload is in flight. New `POST /admin/backup/upload` endpoint.
- **One-click restore from a scheduled backup, from the same Settings > Backup & Restore card.** Picking a listed backup and clicking Restore validates the file (`PRAGMA quick_check`, rejecting anything corrupt or unrelated before touching the live database), gracefully drains in-flight requests, stages the full copy alongside the live `mesh.db` and only swaps it in via an atomic rename once the copy is proven complete (a failure mid-copy leaves the live database untouched), then exits the process. Because the mesh doesn't restart itself, this relies on the deployment's own process supervisor to bring it back up - `docker-compose.yml` now sets `restart: unless-stopped` for exactly this reason, systemd's example unit already has `Restart=on-failure`, and Kubernetes' default `restartPolicy: Always` needs nothing extra. Running the bare binary with no supervisor at all means a restore will stop the mesh and leave it stopped until started manually - `docs/backup.md` calls this out explicitly rather than leaving it a silent surprise, and documents the fully-manual alternative for that case. New `GET /admin/backup/list` and `POST /admin/backup/restore` endpoints back the picker.
- **A model pull is now hard-blocked when the target node doesn't have enough free disk space for it, with no override.** Unlike a VRAM-fit warning, a pull that exceeds free disk WILL fail (partial download, or worst case fills the node's disk and disrupts the OS/other running models) - so unlike the VRAM confirm-anyway dialog, there is no "pull anyway" option here. The check runs both client-side (Model Advisor's Pull button now disables with a "No Disk Space" badge) and server-side (`POST /admin/nodes/{name}/pull` itself now returns 507 before ever starting the download), so it can't be bypassed by calling the API directly. Uses the node agent's existing disk telemetry (`Node.DiskFreeGB`) - no new wire field. Only covers models with a known size today (the curated catalog, and Hugging Face repo browsing where the size comes from HF's own reported file sizes); an arbitrary/uncurated Ollama registry tag has no size to check against and skips the check entirely rather than guessing one. Skipped (never fabricated as "OK") whenever disk telemetry itself is unavailable - no agent, or a non-Linux agent, which doesn't report disk stats yet.
- **Node Agent gained an on-demand "Check now" health probe.** Passive node health already rides in telemetry, but it's only as fresh as the last ~15-30s poll cycle. A new `runtime.health_check` agent capability (`GET /v1/runtime/health`) triggers a real, live liveness probe against the node's own runtime right now - Ollama via `GET /api/tags`, vLLM/TGI/llama.cpp via their real `GET /health`, MLX via `GET /v1/models` (mlx_lm.server has no dedicated health route) - and reports a real ok/error/latency result, never a cached or fabricated one. Surfaced as a "Check now" button in the GPU Nodes page's Manage Node Agent modal, shown only for nodes whose agent reports the capability.
- **Model Advisor now has a per-user Favourites tab.** Star any Hugging Face model while browsing to save it, then switch to the Favourites tab to see just your starred models as a list - no more re-searching every visit. Favourites are scoped to the logged-in admin account (backed by a new `favorites` table keyed on user id), so each operator has their own independent list.
- **Model pulls can now opt into a "verify it loads" check.** A model whose blob downloads fine can still fail to actually load - most often a community Hugging Face GGUF whose declared architecture isn't supported by the node's installed runtime version - and previously the only way to find out was the first real chat request (or the Hardware Benchmark) hitting a cryptic runtime error, long after the pull reported success. Pulling with `"verify_load": true` (a checkbox on the Pull Model modal and Model Advisor, checked by default for community/Hugging Face pulls) now runs one real chat-completion probe (the same one the Hardware Benchmark uses) after the download succeeds and before reporting `success`. A model that fails this probe gets a distinct `load_failed` status with Ollama's real error surfaced verbatim, plus a one-click Delete button right there - nothing is auto-deleted. A model that passes is evicted right back afterward, so a compatibility check never has the side effect of silently keeping a model warm (and possibly displacing whatever was already resident).
- **A hidden hardware benchmark page** for validating the warm-routing speedup on your own hardware without leaving the dashboard. Reachable only via a "Hardware Benchmark" card on Settings (no Sidebar entry - it's a self-service diagnostic, not part of normal operation): pick an already-known node + model, and it runs a live cold-vs-warm Time-To-First-Token comparison through the mesh's own proxy, streaming progress and showing a shareable result card. No manual API key entry needed - the mesh auto-provisions a scoped, ephemeral key for the run and deletes it unconditionally when the job ends (success, failure, or cancel). Results persist to a new `benchmark_runs` history table (`GET /admin/benchmark/runs`).

### Fixed
- **Model Advisor's VRAM fit-check (green/yellow/red) classified against a node's currently-free VRAM instead of its total capacity, producing false "Too Large" verdicts.** Free VRAM shifts with whatever else happens to be warm on the node right now - a model that needed more than the transient free figure but well within the node's total capacity (e.g. a model roughly the size of what's already loaded) was wrongly marked red, even though it would fit fine once other models evict or idle-time-out. The advisor now answers "will this model ever fit on this hardware" (against total VRAM capacity) rather than "does it fit this instant" - that instantaneous check is already routing's job (`free_vram_headroom` placement factor). Separately, the Pull button no longer hard-blocks on a red verdict with only a disabled-tooltip explanation - clicking Pull on a red-flagged variant now shows a confirm dialog ("needs ~X GB, node has ~Y GB total - pull anyway?") so an admin can still proceed when they know better.
- **The "Check now" on-demand health check returned a hard 501 for any node without a Node Agent (or one running a pre-`runtime.health_check` build)**, even though the mesh already runs a real, agent-free liveness probe against every node's runtime on its own periodic poll cycle. `GET /admin/nodes/{name}/health-check` now falls back to that same probe (read-only - it never touches the periodic poller's own health/failure-count state) when no agent capability is available, so the button now works for every node. The "Check now" button (GPU Nodes' Manage Node Agent modal) is no longer gated on agent capability either.
- **The Request Log page could stay empty forever even with real traffic flowing, then double-count every request once audit logging was on, with every row showing a broken "0" status badge.** Five compounding issues: (1) per-request audit logging (the Request Log page's data source) defaulted to off, while the Dashboard's "Live Requests" widget reads a separate always-on in-memory buffer - so a fresh install showed traffic on the dashboard but nothing in the log; (2) that dashboard widget itself displayed the *oldest* entries in its 50-row buffer instead of the newest, so it barely updated under sustained load; (3) toggling audit logging on in Settings updated the database but never reached the already-running logger, so enabling it mid-session silently kept doing nothing until a restart; (4) every request was actually written to `audit_log` twice - once by the proxy's own logging call, and again by a redundant internal write inside `LogRequest` under a separately-generated ID - invisible while audit logging defaulted off, but producing exact duplicate rows the moment it was turned on; (5) the status column stored a semantic label (`warm`/`loading`/`error`) instead of the real HTTP status code the frontend's badge and the server's own success/client_error/server_error filter both expected, so every row showed as a red "0" regardless of actual outcome. Audit logging now defaults to on and applies immediately when toggled, the dashboard widget shows the true latest 10 requests, the Request Log page requests up to 1000 rows instead of silently capping at 50, each request is logged exactly once, and the status column reflects the real response code.
- **The dashboard rendered a blank white page on the `:main` image** - a dependabot PR bumped `react` from 19.2.0 to 19.2.8 without bumping `react-dom` alongside it, and React 19's `react-dom` enforces an exact version match against `react` at mount time, throwing before anything rendered. `react-dom` is now pinned to the same 19.2.8. `scripts/smoke.sh` only exercises API endpoints and never caught this class of failure since it doesn't load the SPA in a browser.
- **The Hardware Benchmark page's model dropdown showed no models at all for a node without a Node Agent (or one still detecting its runtime), even though that node had models on disk.** It only ever consulted the Node Agent's `models.list` capability, falling back to the router's live warm-models view (empty whenever nothing happens to be loaded in VRAM) rather than the same `/admin/models` aggregation the Models page already uses, which queries the node's `/api/tags` directly. It now falls back to that aggregation instead, so all on-disk models show up regardless of Node Agent presence.
- **The Hardware Benchmark page let you pick an embedding-only model (e.g. `mxbai-embed`, `nomic-embed`) and always failed it with a cryptic "does not support chat" error** - the benchmark measures chat-completion Time-To-First-Token, which embedding models have no endpoint for. Ollama's own architecture classification (`details.family` from `/api/tags`) is now threaded through the Node Agent's `models.list` response and the `/admin/models` catalog, and known embedding/encoder families are excluded from the model picker.
- **Cancelling a hardware benchmark run mid-sample didn't actually abort the in-flight request**, so the ephemeral API key it provisioned stayed live for up to 5 minutes (the per-sample timeout) instead of being deleted immediately - `bench.MeasureChatTTFT` now takes a `context.Context` threaded from the job's cancel, so a cancelled cold/warm sample tears down its outbound request right away. Separately, **two benchmark runs started for the same node at nearly the same time could race** - both would pass the "not already running" check before either was recorded, then evict/reload the model out from under each other and corrupt both runs' numbers; the check-and-reserve now happens atomically under one lock before any I/O, so a second run on a busy node gets a `409` instead. Also: the Cancel button was a no-op when a run was started via the in-app Demo Mode toggle rather than the build-time public demo, and an unrecognized progress-stream phase (e.g. from a newer mesh version) could leave the page showing raw text with no way back - both now resolve correctly.
- **An idle (downloaded but not loaded) model on a vLLM/TGI/llama.cpp/MLX node never showed up on the Models page at all.** `GET /admin/models` only ever sourced rows from live warm state and Ollama's `/api/tags` - the Node Agent's own `models.list` capability (already used by the per-node "manage agent" view) was never consulted here, so a downloaded-but-idle model on any non-Ollama runtime was invisible to the Models page's Pull/Delete/Advanced Settings actions. It now also merges in each agent-capable node's idle catalog, skipping any (model, node) pair already reported by the existing two sources so warm counts for Ollama-only fleets are unaffected.
- **A model pull's progress bar vanished on browser refresh, even though the download was still running.** The progress widget tracked pulls in a module-level in-memory map with no persistence - a page reload wiped it, with nothing to re-populate it even though the pull kept running server-side as its own goroutine. A new `GET /admin/pulls` endpoint lists currently-downloading jobs from the mesh's own bookkeeping; the widget now calls it once on mount and resubscribes to each one's progress stream, so a refresh mid-download picks the bar right back up instead of losing it.
- **A newly-pulled model didn't appear on the Models page until the next 5-second poll, or a manual refresh.** The pull-progress tracker and the Models page catalog were entirely decoupled - nothing told the page a pull had just finished. The Models page now listens for pull completions and refetches its catalog immediately when one succeeds, instead of waiting on the next poll tick.
- **A "Ping warmup now" click could silently fail with no visible result, and the Warmup & Scheduling page never refreshed on its own.** The trigger is fire-and-forget on the backend (it returns immediately while the actual per-model pings run in the background), but the page had no polling interval at all - a resulting warmup failure only ever showed up after a manual reload or navigating away and back. The page now polls every 10s (matching GPU Nodes' cadence) and additionally re-fetches a few seconds after a manual ping, so failures surface without a reload.
- **A keep-warm model failing its warmup ping, or a scheduled unload failing, was invisible anywhere except the Warmup page or the mesh's own log output.** The GPU Nodes page already polls every 10s but never surfaced `warmupErrors`, so an operator watching node health during an incident had no clue a keep-warm model was stuck without separately navigating to Warmup & Scheduling. Scheduled unloads had it worse: a failed scheduled/agent unload was only ever logged to stdout, with no dashboard-reachable signal at all - and the schedule itself reported `last_status: ok` regardless, since that status was stamped the instant dispatch started, before the actual (async, per-model) warmup/unload work had even begun. Node cards on GPU Nodes now show a "WARMUP FAILED" / "UNLOAD FAILED" badge (with a per-model tooltip) when either map is non-empty; scheduled warmup/unload now wait for every model's real outcome before the schedule records its status, so `last_status`/`last_error` on `GET /admin/schedules` reflects what actually happened, not just that the node was found.
- **A single dropped Node Agent poll (one TCP blip, one 5-second timeout) instantly blanked all of that node's agent-derived telemetry** (fan/RAM/disk/GPU/runtime status) on the GPU Nodes dashboard, unlike the node's own inference-runtime health, which requires several consecutive failures before flipping unhealthy. Agent polling now uses the same consecutive-failure hysteresis before clearing telemetry or firing an `agent_down` webhook, so a transient blip no longer blanks the dashboard for one cycle. Separately, a rolling-upgrade "agent build is newer than this mesh understands" warning was meant to log once per node but re-logged on every recovery from a transient poll drop - it now latches for real.
- **A Node Agent that started before its local inference runtime (vLLM/TGI/llama.cpp) was up (a routine boot-ordering race on restart or upgrade) permanently omitted that runtime's status and warm-models from every `/v1/status` response for the rest of the agent process's life**, even once the runtime came up moments later - runtime detection only ever ran once, at agent startup. The agent now retries detection on every refresh tick until it succeeds, at effectively no cost once a runtime is found (the retry path is never reached again afterward). Affects all GPU vendors identically (the race is about runtime startup timing, not GPU hardware).
- **Unloading a model on a llama.cpp router-mode node always 400'd "model is not found," even for a model genuinely present.** Callers send the Hugging Face `org/repo` identifier (the same format used everywhere else an HF-cache-sourced model is named), but the router's own model id is a bare filename stem with no substring relationship to `org/repo` at all - so an exact-match lookup could never succeed. Unload now resolves `org/repo` to the router's id by matching each loaded preset's `--model` path, refusing with a clear "ambiguous - N presets match" error (listing the candidate ids) when a repo has more than one quant loaded, rather than guessing.
- **The Node Agent install command shown in the admin UI baked the real, permanent bearer token directly into a copy-pasteable `curl | sh` / PowerShell one-liner**, so it ended up in `~/.bash_history`, SSH session logs, or any runbook/chat message the command got copied into - a durable, cross-machine leak of a token that authorizes pull/delete/unload on that node forever. The command now carries a short-lived (20-minute), single-use enrollment code instead (`ENROLL=<code> MESH=<url>`); `agent service install` exchanges it for the real token over a new `POST /admin/agent/enroll` call, so the permanent token only ever travels in an HTTP response body, never argv or a pasted command. `TOKEN=<token>` keeps working unchanged as a manual fallback for existing scripts.

### Added
- **Node Agent Protocol v1: multi-GPU array, host capacity/identity, runtime version, and a resource-oriented API.** The Node Agent's wire format is renamed and restructured from a narrow "telemetry" schema into the permanent protocol every future node capability builds on. `GET /telemetry` becomes `GET /v1/status`, returning a `{agent, capabilities, host, gpu, runtime, health}` envelope; `POST /actions/pull_model` becomes `POST /v1/models` (pulling a model creates a model resource, capability renamed `actions.pull_model` → `models.pull`); `GET /metrics` is unchanged (left unversioned per Prometheus convention). New data: the `gpu` resource now reports **every** GPU on the host as an array (`gpu.devices[]`, with per-device `core_percent`) plus host-level `driver_version`/`cuda_version` - previously only the first detected GPU was ever reported. `host` gains `ram_total_mb`, `disk_total_gb`, `hostname`, `uptime_seconds`, `boot_time`. `runtime` gains `version` (from `ollama version` where available) and `status` (live reachability), and now also reports `warm_models`. `agent` gains `node_id` - a stable UUID generated once on first install and persisted locally, surviving agent binary upgrades and hostname/IP/DNS changes. The button is now gated on `!demoMode && !isLive`, so Demo Mode can actually demonstrate the pull flow.
- **A small model could be permanently, wrongly reported as "cannot make room" on a node with plenty of real free VRAM, if a much larger sibling keep-warm model was mid-reload at the same time.** Headroom/reservation math (`estimateModelSizeBytes`) estimated a not-yet-loaded model's VRAM need from its on-disk weights size - a reasonable guess before the model has ever been observed loaded, but wrong for any model that doesn't fully fit in VRAM and gets split across GPU+CPU by the runtime (a real case: an 8B Q4_K_M model was ~9.6GB on disk but only used ~3.3GB of actual VRAM once loaded). Every time that model reloaded, its in-flight reservation used the full 9.6GB disk figure instead of its real ~3.3GB footprint, poisoning every other keep-warm model's headroom check on the same node for as long as the reservation lived - a sibling model a fraction of that size could look permanently unfittable even on a node with room to spare. The real, previously-observed VRAM footprint (from the last `/api/ps` poll while the model was actually resident) is now cached per (node, model) and used ahead of the on-disk size the moment it's known, matching the State Hierarchy (live observation beats a derived guess) - the on-disk size is now only ever used before a model's real footprint has been seen for the first time.
- **A scheduled or manual "unload" on a model that's also on a node's keep-warm list got silently undone by the very next warmup ping.** `pingWarmupModels` re-pings every keep-warm model on a fixed interval (default 5m) regardless of why it went cold, so an operator running a "unload gemma4 at night" schedule (or clicking manual unload from GPU Nodes) would see the schedule fire and succeed in the log, only to find the model back in VRAM within minutes - with no error anywhere, since the reload was the warmup ticker doing its job as designed, just fighting the operator's own decision. A manual/scheduled unload now suppresses that model's warmup pings on that node until it's explicitly re-armed - by a "warmup" schedule targeting it, by `WarmModels`, or by toggling the node's keep-warm config again. Auto-eviction under VRAM pressure (LRU headroom) is unaffected and still re-warms on the next tick as before, since that path is meant to be temporary.
- **The Model Fit / Model Advisor VRAM-source badge falsely claimed "nvidia-smi" for any AMD/Intel/Apple Node-Agent-sourced reading.** `handleModelFit`'s source-labeling fell through to a hardcoded `"nvidia-smi"` for any raw source other than the mesh's own local `nvidia`/`declared`, so a ROCm or Intel node's VRAM total displayed the wrong tool as its origin. It now names the actual detected tool (`nvidia-smi`/`rocm-smi`/`xpu-smi`/`system_profiler`), and the GPU Nodes and Model Advisor badges color any of these as a live reading instead of only recognizing the literal string `"nvidia-smi"`.
- **MLX's Advanced Settings showed two controls that silently did nothing, and hid four that actually work.** `seed` and `response_format` were injected into every non-Ollama runtime's request unconditionally, but mlx_lm.server's documented `/v1/chat/completions` schema (SERVER.md) has no equivalent for either - setting them for an MLX model had no effect. Meanwhile `top_k`, `min_p`, `repetition_penalty`, and `logit_bias` - all real, documented mlx_lm.server fields - were hidden from the Advanced Settings modal and never injected, because MLX had been declared with no extra fields beyond the strict-OpenAI base set. Both sides are now corrected against the live mlx-lm source: `seed`/`response_format` are excluded for MLX, and the four real extras are shown and injected.
- **GPU Nodes' CPU stat never showed a real number.** The admin API never serialized the Node
  Agent's collected host CPU utilization at all - `CPUPercent` was polled and stored on the
  node's in-memory state but silently dropped before reaching the JSON response, so the
  dashboard's CPU tile always rendered blank regardless of platform or agent status. It's now
  serialized (`cpuPercent`, gated by `agentPresent` the same way as fan speed/RAM/disk, `--`
  when no agent is reporting) and demo mode only shows a value on the one mock node that has an
  agent, matching how fan/RAM/disk are already demoed. The manage-agent modal copy also now
  mentions CPU usage alongside fan speed, RAM, and disk free.
- **Keep-warm models on a VRAM-constrained node flipped resident/evicted at random instead of settling on a predictable winner.** When two or more models were configured to always stay warm on the same node (via the Warmup page toggle) but didn't fit in VRAM together, the warm loop built its per-node model set from a Go map - whose iteration order is randomized every tick - so which model warmed last (and therefore survived LRU eviction) changed from one warmup cycle to the next. The "keep warm" list order is now treated as an explicit priority hierarchy (first in the list = highest priority): the warm set is built in list order and a higher-priority model can never be evicted to make room for a lower-priority one. The same model now reliably wins every time on a node that can't hold the full set, instead of thrashing. The Warmup page's "Models to keep warm" list is now an explicit, reorderable priority list (numbered rows with up/down controls, same pattern as the cloud-provider priority list in Settings) instead of an unordered toggle grid, so that priority is something you can see and set on purpose rather than an invisible side effect of click order.
- **The time-of-day scroll wheel in the schedule/expiry time picker was over-sensitive and janky on desktop.** Mouse-wheel input translated raw scroll delta directly into scroll position against a hardcoded row-height guess, so a single wheel notch could skip past several values, and snap-back animations could visibly stutter. Wheel input is now normalized to one value per notch (measured against actual row height), decoupled from touch/drag scrolling which still behaves natively.
- **Settings and API Keys pages could freeze permanently mid-navigation** (URL/sidebar updates, page content doesn't) on any build, including the public GitHub Pages demo. `useCurrency`'s cross-tab sync effect called `setPref()` with a freshly-allocated object on every sync, which never equals the previous value by reference - so any two mounted `useCurrency()` instances (the always-mounted budget banner plus whichever of Settings/API Keys was open) endlessly re-triggered each other's sync listener, permanently starving React's ability to commit the next route transition. The sync listener now bails out to the previous object reference when the value hasn't actually changed, matching the value-equality guard already used elsewhere for polling effects.
- **Node Agent's model-pull subprocess (`ollama pull`, `huggingface-cli download`, etc) could panic with `$HOME is not defined`** when the agent ran as a service (systemd or similar) whose own environment had no `HOME` set - the child process inherited that gap and ollama's own CLI has no fallback for it. The agent now guarantees `HOME` is present in the subprocess's environment, resolved from the OS user record when missing, before spawning any pull.
- **GPU Nodes' CPU percentage showed the raw unrounded float** (e.g. `2.3383084577114466%`) instead of a readable two-decimal figure.
- **Loaded models' VRAM size was wildly wrong on the GPU Nodes page** (e.g. a real 3.1GB model showing `3249746.0GB`) - the display divided the model's raw byte count by 1,024 (bytes→KB) and labeled the result "GB" instead of dividing by 1,024³. Now uses the same byte-formatting helper already used correctly elsewhere on the same page.
- **A node added without typing a GPU model name permanently stored the literal string "Unknown GPU" as its label**, rather than treating it as an empty/unset display fallback - so it could never later be auto-filled by real data. Adding a node with the field left blank now sends no model name at all; "Unknown GPU" is purely a display fallback shown when nothing (operator or agent) has set a real one yet.
- **A scheduled "unload" from the Warmup & Scheduling page silently did nothing on vLLM/TGI/llama.cpp/MLX nodes.** The manual unload button (GPU Nodes dashboard) already dispatches through the node's Node Agent when it reports `models.unload`, but the scheduled unload action still only ever called Ollama's own `keep_alive:0` HTTP API directly - worse than the manual case, since a scheduled action has no admin API response to surface an error through, so the no-op was completely invisible. Scheduled unload now shares the same agent-vs-direct decision as the manual path: a node with an agent enabled and reporting `models.unload` dispatches through it; a node with no agent (or an agent that doesn't report the capability) falls back to the direct path completely unchanged.

### Removed
- **Peer health monitor (`ha` config block, `GET /admin/ha/peers`, "Peer Health Monitoring" Settings card) removed.** It only ever polled other ollama-mesh instances' `/health` endpoints for passive observability - no failover, no shared state, no leader election, and it never provided real HA despite the name. ollama-mesh is a single-instance control plane by design (see Architecture Laws); this module's premise (multiple mesh peers) doesn't fit that model, and Node Agent already covers the real multi-machine need (one mesh, many GPU nodes). Anyone who had `ha.enabled: true` set can safely drop it - the `ha` config block and its `ha_*`/`ha_peers` settings keys are silently ignored (not read, not migrated).
- **`GET /admin/config` (and its `/admin/v1/config` alias) removed.** Dead route - no UI caller, no docs, no test coverage. It returned a masked dump of the running config, but Settings.tsx already exposes every editable config field through `/admin/settings`; this was a leftover from before that page existed. `POST /admin/config/reload` (config reload) is unaffected.

## [0.17.0] - 2026-07-17

### Added
- **Node Agent (v1): real GPU/host telemetry for remote nodes, read-only, with a vendor-agnostic collector architecture and a self-installing persistent service.** A new `ollama-mesh agent` subcommand runs a small HTTP server on the GPU node itself, reporting temperature, fan speed, power draw, VRAM, CPU, RAM, and disk free via a versioned JSON schema (`GET /telemetry`) plus a Prometheus-compatible `GET /metrics` derived from it. Telemetry is collected by a background goroutine on a fixed interval (5s default, `--refresh-interval` to tune) into a cached snapshot - `/telemetry` and `/metrics` only ever read the cache, so nvidia-smi never runs on the request path regardless of poll frequency or how many things scrape the node. The payload carries a `last_updated` timestamp so a stale/stuck collector is visible rather than silently serving old numbers as if fresh. The mesh polls it on the existing node poll cycle - no new transport, no WebSockets/gRPC.
  - GPU collection is behind a `GPUCollector` interface (nvidia-smi is the first implementation, selected once at startup from a candidate list) so AMD ROCm, Apple Silicon, and Intel can be added later as new implementations without touching the agent's HTTP server, wire schema, or the mesh-side poller. A CPU-only node (or an unsupported vendor) gets an explicit "no GPU" result, never a fabricated reading.
  - The agent installs itself as a persistent, auto-restarting OS service - `ollama-mesh agent service install` registers with systemd (Linux), launchd (macOS), or a native Windows Service via `sc.exe` (Windows), no new dependencies, no manual unit files or `sc.exe` calls for the operator to write. Re-running install (e.g. after an upgrade, or to rotate the token) reconfigures and restarts the existing service in place.
  - The one-line install command generated from the GPU Nodes page (Linux/macOS via `install.sh`, Windows via the new `install.ps1`) now actually downloads the binary and runs the full service install, instead of assuming the binary already exists and running only in the foreground.
  - Each node gets its own opaque bearer token (AES-256-GCM encrypted at rest, distinct from the mesh's client-facing API keys - a leaked agent token can only feed fake telemetry to one node, not access inference or other secrets). Enable/regenerate/disable an agent from the GPU Nodes page; nodes without an agent installed keep showing `-` for these fields exactly as before, never a fabricated estimate.
  - Agents advertise a `capabilities` list (`["telemetry"]` today) instead of the mesh assuming every agent build supports every feature - future capabilities (models, diagnostics, actions, maintenance) get added to this list in the same change that implements them. Every `/telemetry` response also reports `agent_version`, `schema_version`, `platform`, `architecture`, `gpu_vendor`, and the locally-detected inference `runtime` (if any), surfaced in the GPU Nodes manage-agent modal and as Prometheus labels (`nodeagent_info`) - makes debugging a mixed-version, mixed-vendor fleet possible from the telemetry data alone.
  - **Protocol frozen for rolling upgrades.** Verified (with tests) that an older mesh and newer agents, or a newer mesh and older agents, can coexist in the same fleet indefinitely: unknown fields are always ignored on decode, and every field already treats "missing" as "unknown," never a fabricated zero. The mesh now logs once per node if an agent ever reports a newer `schema_version` than it understands, purely for operator visibility. This is the last planned change to the `/telemetry` wire format before real-world usage.
- **API key expiry is now editable after creation, with time-of-day precision.** Previously `expires_at` could only be set at key creation and had no field at all in the edit modal - once created, a key's expiry could never be added, changed, or cleared. `PATCH /admin/keys/{name}` now accepts `expires_at`, and both the create and edit forms use a combined date/time picker (was date-only on create) so expiry can be scoped to the hour/minute, not just the day.

### Fixed
- **System Audit Trail's action-type dropdown blurred the rows behind it when opened, on both desktop and mobile.** The desktop table wrapper was the only one in the app still using a translucent `bg-card/30 backdrop-blur-sm` background instead of the solid `bg-card` every other page's data table uses, and the mobile card view directly beneath the filter bar had the same translucent-plus-blur combination on each card - so an open dropdown panel bled a frosted-glass effect onto whatever sat underneath it. Both now use a solid `bg-card`, matching the rest of the app.
- **Mobile viewport pass across the whole admin UI.** Every page with a data table (Requests, System Audit, API Keys, GPU Nodes, Users, Routing, Analytics, Dashboard) previously fell back to raw horizontal table-scroll below 768px; each now gets a proper stacked card view with full action parity instead. The date/time picker used site-wide (filters, key expiry, schedules) could render its popup panel past the right edge of a narrow viewport with no clamping - it's now portaled and clamped to stay on-screen at any width. Several pages (Metrics, ModelAdvisor, Warmup, Settings) had individual flex/grid rows that didn't collapse to a single column on narrow screens and now do.
- **Status/action badges (System Audit, GPU Nodes, Requests) used dark-mode-only accent colors** (e.g. bare `text-amber-400`) with no light-mode variant, so they lost contrast against a light background. Now theme-aware (`text-amber-600 dark:text-amber-400` pattern) like the rest of the UI.

### Security
- **Secrets are now encrypted at rest in `mesh.db`.** Cloud provider API keys, mesh-issued API keys, the LiteLLM key, HuggingFace token, and webhook secret were previously stored as plaintext columns/settings - readable by anything with access to the SQLite file (backups, misconfigured storage, a copied `.db`). - **HuggingFace model pull returning Bad Gateway**: the pull proxy waits for the whole download before responding; a hardcoded 5-minute client timeout killed any pull over 5 minutes (routine for multi-GB HF files). Raised to 2 hours.
- **Pinned models could still be unloaded**: the pin check only guarded auto-eviction, never the manual/scheduled unload path. Now blocked (409) on both, and the GPU Nodes page disables the unload button for pinned models.
- **Duplicate node registration**: nodes loaded from config.yaml, the DB store, and Docker discovery were merged with no URL-based dedup - only by exact name - so the same physical node could end up registered twice under different names, splitting its usage/eviction accounting.
- **`install.sh` self-discovery**: the port-8080 probe treated any 200 response on `/health` as a foreign llama.cpp node, so it discovered ollama-mesh's own admin API as a separate node; it now recognizes and skips itself via the unique `proxy_port` field, and skips the host's own IP during the subnet scan.
- **Sidebar/Dashboard version mismatch**: the sidebar showed a stale build-time version while the Dashboard showed the live one; the sidebar now fetches `/health` too.
- **Demo site server clock stuck on "Loading server time…"**: the static GitHub Pages demo (no backend) called the real `/admin/system-info` endpoint, which doesn't exist there, and swallowed the failure. It now returns mock system info like every other demo endpoint.

### Added
- **`SERVICE=1` install mode**: `install.sh` can now set up a systemd unit (`Restart=on-failure`) so ollama-mesh persists across reboots, in addition to the existing install-only and install+probe+run modes.
- **DCO (Developer Certificate of Origin) sign-off requirement** - CONTRIBUTING guidance, a PR-template checkbox, and a CI check.

### Security
- Admin token comparison is now constant-time (`crypto/subtle.ConstantTimeCompare`) to remove a timing side channel.
- Request bodies are capped at 32 MiB (`413` over the limit) to bound a memory-exhaustion DoS vector.
- Admin API no longer sends a wildcard `Access-Control-Allow-Origin: *`. CORS is off by default (same-origin only) and opt-in via `admin.cors_origin`, closing a CSRF/exfil surface on the mutating admin API.

- Usage-state persistence now `fsync`s the temp file and parent directory before the atomic rename, closing a power-loss window that could reset quota counters.
- Config validation rejects non-`http(s)` node and cloud `base_url` values at boot instead of failing per-request later.

### Performance
- Hourly analytics buckets are pruned to a 48h window, bounding memory growth on long-lived processes.

### CI
- CI now runs `go vet`, a `gofmt` gate, `go test -race`, and `govulncheck`.
